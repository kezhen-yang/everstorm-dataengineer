# Everstorm Data Engineer

An AI knowledge-base and production-RAG workshop on Google Cloud, built around a
synthetic outdoor-gear retailer called **Everstorm Outfitters**.

Adapted from Google Cloud's
[Agentverse Data Engineer codelab](https://codelabs.developers.google.com/agentverse-dataengineer/instructions)
([source repo](https://github.com/weimeilin79/agentverse-dataengineer)). Same
architecture, same services, same five parts — the fantasy RPG framing is
replaced with a customer-support scenario that a business audience recognises
immediately.

## What you build

**Hour 1 — a knowledge base with SQL.** 180 free-text support case notes in
Cloud Storage become three queryable BigQuery tables, via an external table and
one `ML.GENERATE_TEXT` call. Then chunk, embed and semantic-search them without
leaving the warehouse.

**Hour 2 — a production RAG agent.** 263 policy-document chunks are vectorised
by a Dataflow pipeline into Cloud SQL with `pgvector`, and served by a Google ADK
agent deployed to Cloud Run behind an A2A endpoint.

```
                    ┌─ BigQuery (analytical) ─────────────────┐
  data/tickets/ ───▶│ external table → ML.GENERATE_TEXT →     │
   180 case notes   │ tickets / orders / resolutions          │
                    │ → chunk → embed → VECTOR_SEARCH         │
                    └─────────────────────────────────────────┘

                    ┌─ Cloud SQL + pgvector (operational) ────┐
  data/kb/ ────────▶│ Dataflow → policy_chunks + HNSW index   │
   263 chunks       │        ▲                                │
                    └────────┼────────────────────────────────┘
                             │ cosine search at query time
                    ┌────────┴────────────────────────────────┐
                    │ ADK agent → A2A → Cloud Run             │
                    └─────────────────────────────────────────┘
```

## The data

Everything is synthetic. `everstorm.example` is an RFC 2606 reserved domain that
can never resolve, and `+1 (406) 555-01xx` is the reserved fictional-use range.
No real company, product, person or PII appears anywhere.

| Path | Count | Feeds |
|---|---|---|
| `data/tickets/*.txt` | 180 | BigQuery external table (Parts 1–2) |
| `data/kb/*.md` | 263 | Dataflow → Cloud SQL (Parts 3–5) |
| `data/tickets_ground_truth.csv` | 180 rows | Scoring the extraction in Part 1 |
| `eval/rag_eval.jsonl` | 32 questions | Scoring retrieval + generation |
| `eval/sql_eval.md` | 5 BI questions | Expected answers for Part 1 |

### Two shapes that matter

**Tickets are one line per file.** The external table reads CSV with a field
delimiter, which yields **one row per line** — not per file. A multi-line ticket
would become ~17 fragment rows and the extraction step would have nothing
coherent to work on. These are pre-flattened.

**KB files are section-level chunks, not whole documents.** The Dataflow pipeline
embeds each *whole file* as one vector and has no chunking stage. A 1,200-word
policy document averaged into a single vector means "shipping, generally" and
retrieves badly. In a real build the split belongs inside the pipeline as a Beam
stage; pre-splitting is a workshop convenience, and the pipeline says so in a
comment.

Both corpora are generated by scripts in the companion notes repo, so you can
change the scale or the planted findings and regenerate deterministically.

### Findings planted in the data

A demo where every aggregate comes back flat teaches nothing. These are real in
the data and will surface from ordinary `GROUP BY`:

- Rotterdam resolves tickets ~3.4 days slower than Reno
- Klarna and Shop Pay tickets stay open longest
- The Summit GTX boot drives 11 of 28 warranty claims, all sole separation
- EU/UK shipping delays cluster in December–January

### Traps planted in the knowledge base

- A **superseded** shipping policy (Rev 3.0, `$99` threshold) sits alongside the
  current one (Rev 4.0, `$75`). Tests recency handling.
- **EU ships DDP, UK ships DDU** — in a document titled for both regions. Tests
  regional disambiguation.
- A **deprecated payments FAQ** states refund timing incorrectly, and two current
  documents explicitly correct it. Tests conflict handling and citation.
- Warranty is 12 months **except** Summit GTX sole separation at 24. Tests
  whether a specific exception beats the general rule.

Because the Cloud SQL schema has no metadata columns, each chunk carries its
document title, revision and status as a **context line in the text**. That is
how version information survives retrieval here; a production build would make
those real columns and filter on them in SQL.

## Quick start

```bash
gh auth login    # the repo is private
gh repo clone kezhen-yang/everstorm-dataengineer ~/everstorm-dataengineer
cd ~/everstorm-dataengineer
chmod +x *.sh
./init.sh                      # creates/selects the GCP project, enables billing
gcloud config set project $(cat ~/project_id.txt) --quiet
```

Enable the APIs, create the Artifact Registry repo, and grant the IAM roles (see
`SETUP.md`), then:

```bash
source ./set_env.sh
./data_setup.sh                # Cloud SQL (~15 min, background) + bucket + upload
```

Verify before starting the session:

```bash
gcloud storage ls gs://${BUCKET_NAME}/tickets/ | wc -l   # 180
gcloud storage ls gs://${BUCKET_NAME}/kb/      | wc -l   # 263
gcloud sql instances describe $INSTANCE_NAME --format='value(state)'  # RUNNABLE
```

## Fill-in-the-blanks markers

`support_agent/agent.py` and `pipeline/vectorize_kb_pipeline.py` ship with
`#REPLACE` markers for the workshop, exactly like upstream. **They will not run
until you fill them in**, and the pipeline file does not even parse, because its
`with` block contains only comments. That is inherited upstream behaviour, kept
deliberately.

Completed reference copies are in `solutions/` — for the instructor to recover
from a bad live edit, not for the student path.

| File | Markers |
|---|---|
| `support_agent/agent.py` | `RAG-CONVERT EMBEDDING`, `RAG-RETRIEVE`, `-CALL RAG` |
| `pipeline/vectorize_kb_pipeline.py` | `EMBEDDING-LOGIC`, `READFILE`, `EMBEDDING`, `WRITE TO DB`, `LOG FAILURES` |

One deliberate change from upstream: the agent embeds the **query** with
`task_type="RETRIEVAL_QUERY"`, not `RETRIEVAL_DOCUMENT`. Both work, since the
vectors share a space, but the asymmetric pairing is correct and it matches the
`VECTOR_SEARCH` example taught in Part 2.

## Cloud SQL schema

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS google_ml_integration CASCADE;

CREATE TABLE policy_chunks (
  id SERIAL PRIMARY KEY,
  chunk_content TEXT,
  embedding VECTOR(768)
);

CREATE INDEX ON policy_chunks USING hnsw (embedding vector_cosine_ops);
```

`VECTOR(768)` must match `text-embedding-005`'s output dimensionality, and
`vector_cosine_ops` must match the `<=>` operator used at query time — mismatch
the latter and Postgres silently ignores the index rather than erroring.

## Hardening: workshop → production

The architecture is genuinely production-shaped — managed services,
containerised, horizontally scalable, IAM-scoped service accounts. These four
corners are cut for the workshop:

- **Secrets.** `DB_PASSWORD` defaults to `1234qwer` in `set_env.sh` and is passed
  to Cloud Run as a plain env var. Use Secret Manager with `--set-secrets`, or
  switch to the connector's IAM database authentication and drop passwords.
- **Public access.** `--allow-unauthenticated` makes the agent callable by
  anyone, and every call costs Gemini tokens. Use IAM-authenticated invocation or
  internal ingress.
- **Availability.** `data_setup.sh` provisions a single zonal Cloud SQL instance.
  Production wants a regional configuration.
- **CI/CD.** The Cloud Build configs build and ship with no test stage. For a
  system whose entire job is factual accuracy, wire `eval/rag_eval.jsonl` into
  the pipeline and gate on the score.
